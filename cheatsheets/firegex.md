# Firegex / regex-фильтры — шпаргалка

Firegex — прокси перед сервисом с regex-фильтрами: быстрый «патч» без правки
кода. **Временная мера**, не фикс: обходится, ломает SLA при ложных
срабатываниях.

## Правила

1. Сначала слушай трафик (Pacmate/tcpdump), потом фильтруй.
2. Фильтр тестируй на **реальных запросах чекера** — ложное срабатывание =
   MUMBLE.
3. Фильтруй точечно (URL+метод+параметр), а не «всё со словом SELECT».
4. Держи откат: выключил фильтр — вернул статус.
5. После фильтра всё равно патч в коде.

## Типовые правила (адаптировать под свой сервис!)

### Path traversal

```
(\.\./|%2e%2e|\.\.%2f|%252e%252e)
```

### Инъекции команд

```
[;&|`$]\s*(id|cat|ls|sh|bash|nc|curl|wget)
```

### SQL-инъекции (грубый)

```
(union\s+select|or\s+1\s*=\s*1|sleep\s*\(\s*\d|benchmark\s*\()
```

### SSTI

```
\{\{.*(__class__|__globals__|__subclasses__|config|lipsum).*\}\}
```

### XXE

```
<!DOCTYPE[^>]*\[|<!ENTITY
```

### Python pickle / Java serialized

```
(gASV|gAJ9|rO0AB)
```

### Чужие сплоиты по UA

Если атакующий ходит стабильным UA (видно в Pacmate) — можно временно резать
именно его, **осторожно**: чекер не должен попасть.

## Чего НЕ делать

- Не блокировать по IP-подсети целиком — там может быть чекер.
- Не фильтровать по коротким общим строкам (`select`, `../../`) — MUMBLE.
- Не ставить `deny all` на сервис «пока разбираемся» — потеря SLA.
- Не забывать URL-декодирование: Firegex видит сырой запрос или декодированный
  — уточни, иначе фильтр мимо.

## Порядок действий при активной атаке

1. В Pacmate нашёл канал утечки флага.
2. Придумал минимальный regex на пейлоад.
3. Прогнал чекер-симулятор / посмотрел легитимные запросы — не задет ли.
4. Включил фильтр, смотришь борду 1-2 тика.
5. Параллельно пишет фикс в код; после деплоя — фильтр снимаешь.
